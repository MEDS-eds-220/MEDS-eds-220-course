18 STAC specification

So far in our course we have obtained data in two ways: by downloading it directly from the data provider or by obtaining a URL from a data repository. These can be convenient ways to access targeted datasets, often using graphical user interfaces (GUIs) for data discovery and filtering. However, relying on clicking and copy-pasting addresses and file names can make our workflows more error-prone and less reproducible. In particular, satellites around the world produce terabytes of new data daily and manually browsing through data repositories can make it difficult to access this data. Moreover, it can be inconvenient to learn a new way to access data from every single big data provider. This is where STAC comes in.

The SpatioTemporal Asset Catalog (STAC) is an open standard for geospatial data that aims to increase the interoperability of geospatial data, particularly satellite imagery. Many major data archives now follow the STAC specification.

In the next classes we’ll be working with the Microsoft Planetary Computer (MPC) STAC API. In this lesson we will learn about the main components of a STAC catalog and how to search for data using the MPC’s STAC API.

Item, collection, and catalog

The STAC item (or just item) is the building block of a STAC. An item is a GeoJSON feature with additional fields that make it easier to find it as we look for data across catalogs.

An item holds two types of information:

  1. Metadata: The metadata for a STAC item includes core identifying information (such as ID, geometry, bounding box, and date), and additional properties (for example, place of collection).

  2. Assets: Assets are links to the actual data of the item (for example, links to the spectral bands of a satellite image).

STAC items can be grouped into STAC collections. For example, while a single satellite scene (at a single time and location) would constitute an item, scenes across time and location from the same satellite can be organized in a collection. Finally, multiple collections can be organized into a single STAC catalog.

For example, we’ll be accessing the MPC STAC catalog. Two of its collections are the National Agriculture Imagery Program (NAIP) collection and the Copernicus Digital Elevation Model (DEM) collection. Each of these collections has multiple items, with each item containing metadata and assets (links to the data).

Application Programming Interface (API)

To request data from a catalog following the STAC standard we use an Application Programming Interface (API). We can think of an API as an intermediary tasked with sending our request for data to the data catalog and getting the response from the catalog back to us. Access

We use the open() method of the Client class from the pystac_client package to access the catalog:

# Access MPC catalog
catalog = Client.open(
    "https://planetarycomputer.microsoft.com/api/stac/v1",
    modifier=planetary_computer.sign_inplace,
)

The modifier parameter is needed to access the data in the MPC catalog.

Notice the output of get_collections() is a generator. This is a special kind of lazy object in Python that you can loop over like a list. Unlike a list, the items in a generator do not exist in memory until you explicitly iterate over them or convert them to a list. This can allow for more efficient memory allocation. Once the generator is exhausted (i.e. iterated over completely), it cannot be reused unless it is recreated.

Catalog search

We can narrow down the search within the catalog by specifying a time range, an area of interest, and the collection name. The simplest ways to define the area of interest to look for data in the catalog are:

  • a GeoJSON-type dictionary with the coordinates of the bounding box,
  • a list [xmin, ymin, xmax, ymax] with the coordinate values defining the four corners of the bounding box.

In this lesson we will look for all the NAIP scenes over Santa Barbara available up to November 16, 2026. The .. at the start of the time range leaves the start date open, so the search returns every scene up to the end date. We’ll use the GeoJSON method to define the area of interest:

# Temporal range of interest
time_range = "../2026-11-16"

# NCEAS bounding box (as a GeoJSON, CRS=EPSG:4326)
aoi = {
    "type": "Polygon",
    "coordinates":[
        [
            [-119.70608227128903, 34.426300194372274],
            [-119.70608227128903, 34.42041139020533],
            [-119.6967885126002, 34.42041139020533],
            [-119.6967885126002, 34.426300194372274],
            [-119.70608227128903, 34.426300194372274]
        ]
    ],
}

# Catalog search
search = catalog.search(
    collections = ['naip'],
    intersects = aoi,
    datetime = time_range)

Before loading the data we want to see how the item intersects with our aoi around NCEAS. To do this, we create a gpd.GeoDataFrame for each of the geometries. The new piece is the shape() function from the shapely package, which turns a GeoJSON-type dictionary into a geometry. Both our aoi and the item’s geometry are GeoJSON-type dictionaries, and STAC geometries always use longitude and latitude coordinates (EPSG:4326).

# Turn the AOI and the item's footprint into geodataframes
aoi_gdf = gpd.GeoDataFrame(geometry=[shape(aoi)], crs='EPSG:4326')
footprint = gpd.GeoDataFrame(geometry=[shape(item.geometry)], crs='EPSG:4326')

Our area of interest is a small part of the item. When we search with intersects, the catalog returns every whole item that touches our area of interest. It doesn’t clip the data to it.

Notice the output doesn’t show any data values, only [526656000 values with dtype=uint8]. That’s because open_rasterio() only read the file’s metadata: its dimensions, coordinates and CRS. The data itself (about 500 MB) stays in the cloud until we use it, for example to plot it or to compute a statistic. This is the same lazy behavior we saw with generators. The NAIP files are stored as Cloud-Optimized GeoTIFFs (COGs), a format designed so we can read just the part of a file we need instead of downloading all of it.

Notice this raster has four bands (red, green, blue, nir), so we cannot plot it directly: .plot.imshow() would read the fourth band (NIR) as transparency. Thus we need to select the bands we want to plot (RGB) before plotting:

# Plot raster with correct ratio
size = 6  
aspect = sb.rio.width / sb.rio.height 
# Select R,G,B bands and plot
sb.sel(band=[1,2,3]).plot.imshow(size=size, aspect=aspect)

The Copernicus Digital Elevation Model (DEM) collection contains elevation data at 90 m spatial resolution [2]. The collection ID in the MPC catalog is 'cop-dem-glo-90'.

  2. Search the catalog for items in this collection that intersect our aoi. How many items did you get?
  3. Get the first item in the search and look at its properties. What is its gsd? What is its datetime?
  4. Before plotting, predict: will this item’s footprint be larger or smaller than the NAIP item’s? Then create a geodataframe with the DEM item’s footprint and plot it together with the NAIP footprint and aoi_gdf.
  5. Open the item’s 'data' asset using rioxarray and save it into a variable named dem. Check its CRS, resolution and nodata value, and plot it.
TipPart B: Is this the data we want?
  1. Obtain the maximum and minimum elevation in dem as numbers, and print them rounded to two decimal places using f-strings. For vertical units, consult the data’s handbook.
  2. Read the collection’s description (catalog.get_collection('cop-dem-glo-90').description). What kind of elevation model is this? Over the NCEAS building, what would it measure?
  3. Look at your plots from steps 4 and 5. Are the maximum and minimum from step 6 the highest and lowest points in Santa Barbara? Where do you think they are?
